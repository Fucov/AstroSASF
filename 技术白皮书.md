一、项目概述
1.1 背景与目标
太空科学实验舱的算力资源极度稀缺且分布不均：GPU 显存容量差异显著（1.5B 小模型 vs 7B 大模型）、通信带宽受限（SpaceWire 200 Kbps）、硬件故障不可预测。AstroSASF 旨在构建一个通用、可扩展、容错的智能体调度框架，在上述极端约束下实现高效的分布式任务编排。

1.2 核心设计哲学
原则	说明
零业务词汇	内核层（infra/、scheduler/）完全使用通用术语，无航天/实验舱领域词汇
高内聚	每层职责单一，通过接口而非实现耦合
纯异步	全部使用 asyncio，无同步阻塞调用
配置驱动	所有行为通过 config.yaml 外部化，无需修改代码
透明降级	网关层自动处理算力降级，上层 Agent 无需感知
1.3 版本演进
版本	核心能力
V7.0	DAG 双轨调度（理论 Planner / 实践 Worker 分离）
V7.2	分布式网关重构（多后端负载均衡 + VRAM 熔断）
V7.3	PromptTransformationPipeline（RAG + StaticMCP + SpeculativeWarmer）
V7.4	OoO 乱序越级执行 + ActiveResourceTable 五层防死锁
V7.5	异构计算调度（意图感知模型路由 + 动态透明降级）

三、接口层 — 北向 API（interface/）
3.1 定位
北向接口层是整个框架对外暴露的唯一 HTTP 入口，采用 FastAPI 实现。它负责：

协议适配：将外部 HTTP 请求转换为内部数据模型
会话聚合：通过 APIFacade 聚合网关、调度器、实验室加载器
Agent C/S 解耦：所有 Agent 均以 HTTP 客户端身份通过此层访问内核

4.1.2 PromptTransformationPipeline（transform_pipeline.py）
设计原则：流量拦截与 Prompt 重构，对上层 Agent 完全透明。 四个中间件：

中间件	作用	节省 Token
RAGReorderMiddleware	相关 SOP 文档检索 + 重排到前缀	~200-500

流式响应净化：逐 SSE chunk 检查，包含不完整 <think> 标签的 chunk 整块丢弃。

4.2 请求路由层（infra/routing/）
4.2.1 PrefixAwareLoadBalancer（prefix_balancer.py）
V7.5 核心增强：意图感知 + 异构算力路由。 意图检测规则：

# agent_id 前缀正则匹配（优先级最高）
"planner_*"   → AgentIntent.PLANNER → compute_class="heavy"
"executor_*"  → AgentIntent.EXECUTOR → compute_class="light"
"worker_*"    → AgentIntent.EXECUTOR → compute_class="light"
"qa_*"        → AgentIntent.QA → compute_class="light"
(其他)         → AgentIntent.FALLBACK → compute_class="heavy"(默认)
# tags 关键词匹配（fallback）
"planner" in tags → heavy
"exec"/"tool" in tags → light
"qa"/"question" in tags → light
路由决策流程（V7.5）：

1. 意图检测
   agent_id/tags → AgentIntent → required_compute_class
2. CRITICAL 跳过亲和
   priority=="CRITICAL" and not prefer_cached → 直接 Least-Connections
3. 亲和路由（含 compute_class 过滤）
   Hash 命中 AND compute_class 匹配 AND VRAM < High WM
   → 直连（SGLang RadixAttention KV-Cache 复用）
4. 意图降级路由（V7.5 核心）
   required_compute_class=="heavy" 且 heavy 实例不可用
   → 自动降级到 light 实例（透明）
5. Least-Connections 兜底
   → 按 compute_class 过滤后最少连接选择
Prefix Hash 算法：

def compute_prefix_hash(prompt: str, system_prompt: str | None) -> str:
    # 1. SOP 标识符提取
    # 2. System Prompt 前 200 字符
    # 3. 任务描述前缀（中文）
    # 4. 代码块内容提取
    # 5. 兜底：prompt 前 100 字符

4.2.2 VRAMWatermarkBreaker（vram_breaker.py）
优先级感知的显存熔断器，结合熔断器状态机：

优先级	允许最高 VRAM	策略
CRITICAL	100%	强制放行（硬件报警优先）
HIGH	92%	超过 Critical 拒绝
NORMAL	85%	超过 High 拒绝
LOW	60%	超过 Low 拒绝
熔断器状态机：		
CLOSED → (连续 N 次拒绝) → OPEN
OPEN → (timeout 30s) → HALF_OPEN
HALF_OPEN → (测试请求成功) → CLOSED
HALF_OPEN → (测试请求失败) → OPEN

5.3 V7.4 OoO 乱序越级执行
问题：传统 DAG 调度必须严格按拓扑顺序，当 ReadyQueue 为空但 Worker 有空闲时，资源浪费。 解决方案：当 RunningNodes < max_workers 且 BlockedQueue 非空时，调度器主动遍历 BlockedQueue 执行三重准入门检查：

┌─────────────────────────────────────────────────────────┐
│  OoO 越级提取 — 三重准入门                                 │
│                                                          │
│  Gate 1: 逻辑依赖检查                                     │
│    all(dependencies[dep_id].status == COMPLETED)        │
│                                                          │
│  Gate 2: 资源锁检查 (ActiveResourceTable)                │
│    all(resource.is_free for resource in required)        │
│    → 按字母序依次加锁（防死锁）                            │
│                                                          │
│  Gate 3: 联锁引擎检查                                     │
│    InterlockEngine.check(node)                            │
└─────────────────────────────────────────────────────────┘
    │ 三门全通过
    ▼
  原子性资源预约（在 _ooo_lock 下）
    │
    ▼
  节点移入 ReadyQueue → 被空闲 Worker 抢到执行
五层防死锁策略：

层级	策略	防止的死锁类型
1	字母序加锁协议	循环等待
2	三重准入门原子预约	检查-预约竞态
3	节点完成自动释放资源	资源泄漏
4	推进保证（每次推进立即更新资源表）	幽灵锁
5	超时降级兜底（2s）	极端情况

5.5 硬件级抢占机制
TelemetryBus 监测危险条件 → 注入 CRITICAL 逃生任务 → Cancel 所有 LLM 推理：

async def _handle_hardware_interrupt(interrupt: HardwareInterruptTask):
    await self._cancel_all_llm_tasks(reason=interrupt.description)
    for node in self._running_nodes:
        node.mark_skipped()          # 挂起当前任务
    escape_node = interrupt.to_dag_node(priority=CRITICAL)
    await self._enqueue_ready_node(escape_node)  # 注入逃生任务
5.6 动态优先级 Aging
防止低优先级任务饿死：随着等待时间增长，优先级动态提升。

# Dynamic_Score = Base_Score - min(Aging_Boost, Max_Boost)
# Aging_Boost = (Current_Time - Submit_Time) * Aging_Factor
def compute_dynamic_priority(base_priority, submit_time) -> float:
    elapsed = now - submit_time
    aging_boost = min(elapsed * 0.1, 10.0)  # 最多提升 10 级
    return float(base_priority.value) - aging_boost

八、异构计算调度 — V7.5 核心创新
8.1 问题定义
太空 GPU 算力极度不对等：

大显存卡（V100/A100）：运行 7B+ 模型，适合复杂 DAG 规划
小显存卡：运行 1.5B 模型，适合简单 Tool Calling 参数提取 传统网关对所有请求一视同仁，造成算力碎片与浪费。
8.2 解决方案：异构算力池 + 意图感知路由
Agent 请求
    │
    ├── agent_id="planner_agent_01"  ──┐
    │                                    │ 意图检测
    ├── tags=["planner"]              ──┤    │
    │                                    │    ▼
    │                               AgentIntent.PLANNER
    │                                    │    │
    │                                    │    ▼ compute_class="heavy"
    │                                    │    │
    │                                    │    ▼
    │                           PrefixHash 亲和路由
    │                                    │
    │                                    │
    ├── agent_id="executor_worker_03"  ──┤
    │                                    │ 意图检测
    └── tags=["executor"]              ──┘    │
                                               ▼
                                    AgentIntent.EXECUTOR
                                               │
                                               ▼ compute_class="light"
                                               │
                                               ▼
                                    直接路由到 light 实例
8.3 动态透明降级
当 heavy 实例 VRAM 超 85% 时，自动降级到 light 实例，不返回 503 拒绝：

请求: model="qwen2.5:7b", priority="NORMAL", agent_id="qa_agent_01"
        │
        ▼ 意图检测
    QA → compute_class="light" (优先)
        │
        ▼ 亲和路由查找 heavy 实例
    heavy 实例 VRAM=92% → 跳过
        │
        ▼ 意图降级路由
    自动路由到 light 实例
        │
        ▼ 透明替换模型
    实际使用: qwen2.5:1.5b
        │
        ▼ 标记元信息
    GatewayResponse:
        downgraded=True
        compute_class="light"
        downgrade_reason="算力降级: qwen2.5:7b → qwen2.5:1.5b ..."
